# Сборка словаря

Этот процесс собирает словарь Russian Diceware 4d6 из итогового списка слов и редактируемого содержания.

## Шаги

### 1. Внести правки

Отредактировать содержание в `data/dictionary/dictionary.tex` или макет в `data/dictionary/dictionary-layout.tex`.
Если нужны изменения словарных данных, внести их на предыдущих этапах и заново собрать `data/wordlist/wordlist.csv`.

### 2. `01-build-dictionary.ts`

Читает:
- `data/wordlist/wordlist.csv`
- `data/dictionary/dictionary.tex`
- `data/dictionary/dictionary-layout.tex`
- `data/dictionary/last-release.json`
- шрифты и лицензии из `data/external/fonts/`

Создаёт в `data/dictionary/output/`:
- `russian-diceware-4d6.pdf` — словарь с изданием и редакцией на обложке
- `russian-diceware-4d6.csv` — побайтовую копию итогового CSV
- `russian-diceware-4d6.tsv` — те же столбцы, значения и порядок строк с табуляцией как разделителем
- `release.json` — версию, отпечаток словарных данных, контрольные суммы файлов и исходников и Git `commit`

Логика шага:
- выбирает версию по последнему опубликованному выпуску
- собирает PDF и проверяет его на ошибки вёрстки
- заменяет весь предыдущий локальный комплект, не оставляя устаревших файлов
- при ошибке компиляции сохраняет временный каталог с журналом и не изменяет `output/`

Комплект игнорируется Git. Сборка не меняет запись о последнем выпуске, не создаёт тег и не обращается к GitHub.
В `release.json` записывается текущий HEAD. Точные версии использованных исходников фиксируются контрольными суммами.

### 3. Проверить комплект

Открыть PDF из `data/dictionary/output/` и проверить содержание и макет.
Если нужны правки, повторить шаги 1 и 2, затем проверить новый PDF.
Для выпуска использовать только последний проверенный комплект без повторной сборки.

### 4. `02-publish-release.ts`

Читает:
- проверенный комплект из `data/dictionary/output/`
- вручную подготовленное описание выпуска из `data/dictionary/output/release-notes.md`
- исходники, перечисленные в `release.json`
- `data/dictionary/last-release.json` и состояние выпусков на GitHub

Создаёт:
- тег и GitHub Release с комплектом, если выпуск ещё не опубликован
- обновлённую запись о последнем выпуске в `data/dictionary/last-release.json`, отдельный `commit` и `push` в `main`

Логика шага:
- проверяет целостность комплекта и согласованность версии перед публикацией, не пересобирая файлы
- публикует проверенный комплект в GitHub Releases и после проверки выпуска обновляет локальную запись, выполняет `commit` и `push` в `main`
- не заменяет опубликованный выпуск, а при повторном запуске завершает прерванное обновление локальной записи или Git
- останавливается при расхождении с GitHub или наличии неполного черновика либо тега без выпуска

Выводит результат:
- `published` — создан новый выпуск, для локальной записи выполнены `commit` и `push` в `main`.
- `reconciled` — выпуск уже существовал на GitHub, но локальная запись ещё не обновилась. Скрипт проверил выпуск и обновил запись.
- `recorded` — выпуск и запись уже существовали. Скрипт проверил их и при необходимости завершил прерванный `commit` или `push`.

## Выбор версии

`data/dictionary/last-release.json` содержит только последний опубликованный выпуск в поле `lastRelease`. До первой публикации это поле равно `null`. Запись содержит положительные целые `edition`, `revision` и `wordlistSha256` из сведений опубликованного комплекта. Для выбора следующей версии доступ к GitHub не нужен.

История выпусков хранится в GitHub Releases, а предыдущие состояния локальной записи — в истории Git.

- Выпусков ещё не было — `ed1-rev1`.
- Данные совпадают с последним опубликованным выпуском — следующая редакция того же издания.
- Данные изменились — следующее издание с первой редакцией.

Для выбора версии сравниваются содержание и порядок словарных данных. Повторные сборки до публикации сохраняют номер выпуска. Пробные сборки не меняют запись о последнем выпуске.

## Порядок запуска

### 1. Один раз установить Node.js

Установить [Node.js 24](https://nodejs.org/en/download) с npm и проверить версии:

```bash
node --version
npm --version
```

### 2. Один раз установить TeX Live

1. Скачать [официальный установщик TeX Live](https://www.tug.org/texlive/acquire-netinstall.html) для своей платформы. Для macOS и Linux распаковать архив и запустить `perl install-tl --scheme=infraonly` из распакованного каталога. Для Windows запустить установщик `.exe`.

2. Выбрать набор `scheme-infraonly` (только инфраструктура TeX Live) и каталог установки. На Windows выбор набора доступен в расширенных настройках установщика. Подробности — в [инструкции TeX Live](https://www.tug.org/texlive/quickinstall.html).

3. Добавить каталог исполняемых файлов TeX Live в `PATH`. Он находится внутри каталога установки в `bin/<платформа>`, например `bin/universal-darwin` на macOS или `bin/windows` на Windows. Открыть новый терминал и проверить:

   ```bash
   tlmgr --version
   ```

4. Установить LuaLaTeX, latexmk и пакеты для макета. Зависимости пакетов `tlmgr` добавит автоматически:

   ```bash
   tlmgr install latex-bin luahbtex luatex luaotfload lualatex-math lm latexmk fontspec babel babel-russian hyphen-russian geometry graphics xcolor tools colortbl fancyhdr hyperref
   ```

   Проверить установку:

   ```bash
   lualatex --version
   latexmk --version
   ```

### 3. Один раз установить GitHub CLI

Установить [GitHub CLI](https://cli.github.com/) и проверить установку:

```bash
gh --version
```

Авторизовать `gh` под учётной записью с правом записи в `igor-malinyak/Russian-Diceware-4d6`:

```bash
gh auth login
gh auth status
```

Для токена с гранулярными правами требуется разрешение `Contents: write`. Для завершающего `git push` также нужен настроенный доступ Git к `origin` и право выполнять `push` в `main`.

### 4. Один раз установить зависимости скрипта

Из корня репозитория:

```bash
cd pipelines/dictionary
npm ci
```

### 5. Собрать комплект

После правок и подготовки итогового списка слов выполнить `commit` и `push` исходников в `main`. Затем запустить из `pipelines/dictionary/`:

```bash
node 01-build-dictionary.ts
```

### 6. Опубликовать проверенный комплект

После ручной проверки локального комплекта подготовить `data/dictionary/output/release-notes.md` с описанием изменений выпуска в формате Markdown. Этот файл остаётся локальным, а опубликованный текст хранится в описании GitHub Release. Заметки готовятся после финальной сборки, поскольку пересборка заменяет весь `output/`.

Затем запустить из чистой ветки `main`, находясь в `pipelines/dictionary/`:

```bash
gh auth status
node 02-publish-release.ts
```
